# DroneDoctor 对话诊断优化 PRD（简化版）

> 版本：v1.0 | 日期：2026-06-04 | 范围：统一诊断架构 v2.0 交互层优化

---

## 1. 项目概述

让 DroneDoctor 的诊断流程真正"认识"用户——前端输入的机型信息不再丢失，决策树能根据上下文动态调整路径，诊断结论基于用户实际交互动态计算概率，而非硬编码。

---

## 2. 用户需求与痛点

### 目标用户
- **主力**：16-35 岁无人机维修学员（白天在机构学实操，晚上用工具练诊断）
- **次要**：维修师、机主

### 核心痛点
| 痛点 | 场景 | 用户原话（推测） |
|------|------|----------------|
| 信息白填 | 首页选了 Mavic 3，诊断过程又问一遍机型 | "我明明选了机型，怎么还问" |
| 流程僵化 | 回答"不确定"后被直接判为 no 分支 | "我想再确认一下，系统直接走下一步了" |
| 结论虚浮 | 认真回答每一步，概率永远是 45%/25%/15% | "这概率是固定的吧？跟我回答没关系" |

### 期望目标
- 诊断流程感知用户已提供的信息，自动跳过重复步骤
- 模糊回答能触发追问，而非强行分支
- 结论概率随用户交互动态变化，体现"越回答越精准"

## 3. 功能边界与优先级

### P0（MVP，Phase 1 — 1-2 天）
**机型全链路贯通**
- [x] 前端结构化信息（deviceType/model）传入后端 API
- [x] IntentParserService 优先消费 hints，不再忽略前端输入
- [x] 会话上下文（session.treeExecution.context）携带机型信息
- [x] 决策树起始节点能读取 context，自动跳过已确认信息

> **范围外**：不新增 `input` 节点类型，不改决策树 JSON Schema，先让现有字段跑通。

### P1（Phase 2 — 2-3 天）
**动态路径引擎**
- [ ] 引入 DynamicPathService，支持节点条件跳过
- [ ] `resolveBranch` 支持 `clarify` 追问状态
- [ ] 在一棵决策树（建议 `tree-battery`）上试点

> **范围外**：暂不引入 `weights` 权重和 Evidence Board。

### P2（Phase 3 — 3-4 天）
**证据驱动的智能结论**
- [ ] Evidence Board 动态概率计算（替代硬编码）
- [ ] AI 阶段性综合诊断（每 3 步触发）
- [ ] 前端实时诊断洞察展示

> **范围外**：权重数据需维修专家并行提供，非开发阻塞项。

### 明确不做（Out of Scope）
- 不重构统一诊断架构的四大服务边界（IntentParser/TreeRouter/TreeExecutor/DiagnosisGenerator）
- 不新增决策树数量（保持现有 5 棵）
- 不改动前端首页三步输入的 UI 结构
- 不引入新的 AI 模型，继续使用现有 Kimi API

## 4. 成功指标与验收标准

### KPI

| 指标 | 基线 | 目标 | 测量方式 |
|------|------|------|---------|
| 机型信息利用率 | 0%（当前完全丢失）| 100%（前端选了即带入会话）| 日志：session.context.deviceType 非空率 |
| 用户完成诊断率 | — | 提升 15% | 埋点：diagnosis_complete / diagnosis_start |
| 诊断结论置信度合理性 | 固定分布 | 与用户交互相关 | 抽样 10 个场景，专家评估概率与回答的匹配度 |

### 验收条件

**P0 验收（Phase 1 结束）**
- [ ] 前端选择"Mavic 3 系列"后，调用 `/api/diagnosis/unified`，返回的 session 中包含 `context.deviceType: "mavic"`
- [ ] 同一用户再次进入交互式诊断，日志显示未重复询问机型
- [ ] 现有 5 个测试用例（compass/power_on/takeoff/battery/camera）全部通过回归

**P1 验收（Phase 2 结束）**
- [ ] `tree-battery` 决策树中至少 1 个节点支持 `conditions.skipIf`
- [ ] 用户回答"不确定"时，后端返回 `decision: "clarify"`，前端不推进节点
- [ ] 预测路径与 BFS 默认路径存在差异（至少 1 个场景）

**P2 验收（Phase 3 结束）**
- [ ] 同一 terminal 节点，不同 branchHistory 返回不同 `possibleCauses` 概率分布
- [ ] Evidence Board 的 `topHypothesis` 与专家判断一致率 >= 70%
- [ ] 前端展示"当前最可能：XX（置信度 YY%）"区域

## 5. 风险与待确认

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Phase 3 需要维修专家填分支权重 | 可能延期 | 开发先做框架，权重可后补；专家资源由业务方协调 |
| 动态路径可能让用户感到"跳跃" | 体验下降 | skippedNodes 需前端显式展示"已自动跳过 X 项" |
| clarify 状态增加交互轮次 | 完成率下降 | 仅在高置信度模糊词（"不确定"/"不知道"）时触发 |

### 待确认问题
1. 前端机型选择器的选项值（`mavic` / `mavic3` / `mini4` 等）是否需要与后端统一枚举？
2. 决策树 JSON 的修改权限——是否由开发直接改，还是需业务方审核？
3. Phase 3 的权重数据，维修专家预计多久能提供？
